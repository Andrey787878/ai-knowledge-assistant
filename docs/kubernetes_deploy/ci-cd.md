# CI/CD для этапов B и C

Этот документ описывает контур поставки изменений для Kubernetes-контура
этапов B и C: как устроены `CI`, `CD`, собственный runner, частичная выкладка
по областям и проверки после выкладки.

## Что описывает документ

Этап B поднимает `k3s`-контур и прикладные Helmfile-слои. Этап C добавляет
поверх него автоматическую проверку инфраструктурного кода, выкладку из
GitHub Actions и правила безопасного применения изменений в production.

Контур разделен на две части:

- `CI` валидирует репозиторий и не трогает кластер;
- `CD` выполняется внутри инфраструктурного периметра через отдельную VM
  `runner`, у которой есть доступ к `k3s` API и ключам для расшифровки
  зашифрованных значений.

## Модель поставки

Текущая модель простая и предсказуемая. Источником истины остается репозиторий,
а применение изменений в кластер идет только через GitHub Actions на
собственном runner-хосте.

Ожидаемая операционная модель:

- рабочие изменения вносятся через feature-ветки и pull request;
- ветка `main` используется как основной production-источник состояния;
- автоматическая выкладка в production запускается только для коммита,
  который уже попал в `main` и успешно прошел `CI`;
- ручной деплой используется для полного повторного применения, точечной
  выкладки одного слоя и контролируемого повторного запуска, но тоже не
  обходит проверку качества.

Если branch protection для `main` еще не включен в настройках GitHub, этот
документ все равно исходит именно из такой целевой модели.

## Что входит в CI

Основной workflow:

- `.github/workflows/ci.yml`

CI не зависит от кластера и служит входной проверкой качества перед merge.

Сейчас в CI уже проверяются:

- YAML и workflow-файлы;
- `n8n` workflow JSON;
- `gitleaks` secret scan;
- `terraform fmt`, `terraform validate`, `tflint`;
- Helm/Helmfile template-валидация;
- `bash -n` и `shellcheck` для служебных скриптов;
- Ansible syntax-check.

Этот слой нужен, чтобы ловить типовые ошибки до того, как они попадут в
production-контур.

## Что входит в CD

Контур выкладки построен вокруг двух workflow:

- `.github/workflows/cd-k3s-auto.yml`
- `.github/workflows/cd-k3s-manual.yml`

Оба workflow запускаются не на GitHub-hosted runner, а на отдельной VM
`runner`, которая создается Terraform-стеком `deploy/terraform/k3s_deploy` и
подготавливается ролью `github_runner`.

Runner зарегистрирован с labels:

- `self-hosted`
- `linux`
- `x64`
- `k3s`
- `prod`
- `deploy`
- `stage-b`

`runs-on` у workflow выкладки завязан именно на этот набор labels. Это защищает
контур от случайного запуска на неподготовленном хосте без `kubectl`,
`helmfile`, `sops` и `kubeconfig`.

## Почему runner вынесен в отдельную VM

Runner не совмещается с control-plane-нодой `k3s`. Это отдельная VM в том же
инфраструктурном контуре.

При этом runner не обязан иметь публичный IP: в текущей целевой схеме это
private-only VM, которая попадает в inventory group `private_hosts -> github_runners` и
обслуживается через `ProxyJump` от публичного `k3s`-хоста.

Такое разделение дает три практических эффекта:

- CD не конкурирует с control-plane и workload-подами за CPU и память;
- жизненный цикл GitHub runner не смешивается с жизненным циклом кластера;
- права, firewall и операционная диагностика у хоста выкладки остаются
  отдельными от `k3s`-ноды.

С точки зрения операционной модели runner — это внутренний хост выкладки для
этапов B и C.

В текущей конфигурации runner использует тот же `preemptible` режим, что и
основная `k3s` VM. Это снижает стоимость, но делает CD-контур зависимым от
доступности этой VM:
если VM была прервана облаком, workflow не сможет стартовать, пока runner не
вернется в строй и не зарегистрируется снова как рабочий хост.

## Как устроен runner-хост

Runner host готовится ролью:

- `deploy/kubernetes/bootstrap/roles/github_runner`

Во время bootstrap на runner настраиваются:

- GitHub Actions runner как systemd-сервис;
- `kubectl`, `helm`, `helmfile`, `sops`, `age`, `helm-secrets`;
- `KUBECONFIG=/home/github-runner/.kube/config`;
- `SOPS_AGE_KEY_FILE=/home/github-runner/.config/sops/age/keys.txt`;
- доступ к `k3s` API по private endpoint;
- локальный набор данных для расшифровки зашифрованных SOPS-значений.

Сетевой доступ runner к `k3s` API специально зажат с двух сторон:

- на runner разрешён egress `6443/tcp` только к private IP `k3s`;
- на `k3s` разрешён ingress `6443/tcp` не только от внешних admin CIDR, но и
  от private IP runner VM.

Это схема с минимально необходимыми правами: хост выкладки может достучаться
до Kubernetes API, но не получает лишнего сетевого доступа внутри подсети.

Отдельно важно, что для выхода runner в интернет используется не публичный IP,
а `NAT Gateway + route table` в Terraform-инфраструктуре этапа B. За счет этого
runner может скачать пакеты, достучаться до GitHub и registry, но не получает
собственную публичную точку входа.

Секретная модель у runner двусоставная:

- короткоживущий GitHub registration token для первичной регистрации runner;
- `age` private key для `sops`/`helm-secrets`, чтобы workflow могли применять
  encrypted Helm values.

Оба секрета не хранятся в репозитории и должны попадать только в локальные
`zz-local.yml` файлы bootstrap inventory.

Откуда берутся значения:

- `github_runner_registration_token`:
  `Settings -> Actions -> Runners -> New self-hosted runner`
- `github_runner_sops_age_key`:
  существующий локальный `~/.config/sops/age/keys.txt`, который уже
  расшифровывает проектные `*.enc.yaml`

## Автоматическая выкладка

Workflow:

- `.github/workflows/cd-k3s-auto.yml`

Trigger:

- `workflow_run` после завершения `.github/workflows/ci.yml`

Логика автоматической выкладки:

1. `CI` завершается для конкретного коммита;
2. автоматическая выкладка стартует только если:
   - `CI` завершился со статусом `success`;
   - `head_branch == main`;
   - исходное событие было именно `push`;
3. workflow получает актуальное состояние `main` и отдельно проверяет, что SHA
   завершившегося `CI` все еще совпадает с актуальным tip `origin/main`;
4. если за время ожидания в `main` уже попал более новый коммит, workflow
   корректно помечает себя как устаревший и не трогает production;
5. если run актуален, выполняются:
   - `deploy-k3s-scope.sh all`
   - `smoke-k3s-scope.sh all`
6. после успешной выкладки SHA сохраняется как последний полный успешный deploy;
7. итог записывается в `GITHUB_STEP_SUMMARY`.

Такая схема важна по двум причинам:

- зеленый `CI` на feature-ветке сам по себе не может задеплоить production;
- CD привязан именно к актуальному состоянию ветки `main`, а не к устаревшему
  workflow run из очереди или ручного rerun.

## Ручная выкладка

Workflow:

- `.github/workflows/cd-k3s-manual.yml`

Trigger:

- `workflow_dispatch`

Ручной деплой поддерживает три режима:

- `full` — полное применение корневого Helmfile;
- `scope` — точечная выкладка одного слоя;
- `changed` — выкладка только измененных областей для выбранного `ref`.

Дополнительно ручной workflow требует явного подтверждения через input
`confirm_prod=DEPLOY`. Это простой предохранитель от случайного ручного
выката в production.

Перед самой выкладкой workflow ручного запуска делает отдельную предварительную
проверку:

- проверяет через GitHub Actions API, что для выбранного `ref` или `sha`
  существует успешный `push`-запуск workflow `CI`;
- если такого run нет, workflow останавливается с понятной ошибкой до любого
  обращения к кластеру.

Это означает, что ручной путь не является обходом проверки качества. Он просто
дает оператору более явный контроль над тем, какой именно уже
провалидированный ref нужно выкатить.

Режим `changed` стоит воспринимать как вспомогательный режим, а не как самый
строгий операционный путь. Он полезен, когда diff хорошо понятен и нужно быстро
переиграть частичную выкладку без полного повторного применения. Для максимально
предсказуемого production-сценария предпочтительнее `scope` или `full`, потому
что они не зависят от вычисления diff.

## Модель по областям выкладки

CD работает не по сервисам в общем смысле, а по конкретным Helmfile-слоям.

Поддерживаемые scope:

- `platform`
- `observability`
- `postgres`
- `redis`
- `wiki`
- `ollama`
- `n8n`
- `all`

Соответствие файлов и scope задается в:

- `.github/scripts/cd/detect-k3s-scopes.sh`

Текущая логика такая:

- изменение `deploy/kubernetes/helmfile.yaml` ведет к `all`;
- изменение внутри конкретного layer path ведет только к соответствующему
  scope;
- изменения в `deploy/kubernetes/vendor_charts` мапятся к соответствующим
  областям выкладки;
- изменения только в `docs`, `README.md`, картинках и другой недеплойной
  документации не запускают deploy.

Это делает CD быстрее и понятнее с точки зрения области затронутых изменений.

Для `workflow_dispatch` в режиме `changed` workflow использует в качестве базы
SHA последнего полного успешного deploy, сохраненный в кластере. Иными словами,
changed-режим отвечает не на вопрос "что поменялось в последнем коммите", а на
вопрос "что изменилось со времени последней полной успешной выкладки". Если
такой базы еще нет, workflow безопасно переходит к полному deploy.

## Скрипты деплоя

Весь исполняемый контур CD вынесен в явные bash-скрипты:

- `.github/scripts/cd/detect-k3s-scopes.sh`
- `.github/scripts/cd/delivery-state.sh`
- `.github/scripts/cd/deploy-k3s-scope.sh`
- `.github/scripts/cd/smoke-k3s-scope.sh`
- `.github/scripts/cd/verify-ci-success.sh`

Такой подход выбран сознательно. Сложная логика остается не в YAML workflow, а
в обычных скриптах, которые можно:

- читать отдельно от GitHub UI;
- lint-ить через `shellcheck`;
- проверять через `bash -n`;
- переиспользовать локально при диагностике.

Отдельный `verify-ci-success.sh` здесь особенно важен: логика проверки
качества живет не в разрозненных YAML-условиях, а в явном скрипте с понятным
сценарием ошибки.

## Проверки после деплоя

Каждая область после `helmfile sync` проходит свой набор проверок.

Примеры:

- `platform` проверяет namespaces, `cert-manager` и `ClusterIssuer`;
- `observability` проверяет `Prometheus`, `Alertmanager`, `Grafana`, `Loki`,
  `Alloy` и наличие `ServiceMonitor`/`PrometheusRule`/`Probe`;
- `postgres` проверяет StatefulSet, service и backup CronJob;
- `wiki` и `n8n` делают не только rollout status, но и HTTP health-check через
  `kubectl port-forward`;
- `ollama` проверяет `/api/version`.

Это не заменяет полноценную сквозную приемку, но хорошо закрывает
контракт «релиз применился и базово отвечает».

## Защитные механизмы

В контуре production сейчас есть несколько сознательных предохранителей:

- автоматическая выкладка стартует только после успешного `CI` для коммита в `main`;
- ручная выкладка требует `confirm_prod=DEPLOY`;
- ручная выкладка отдельно проверяет успешный `CI` для выбранного `ref`;
- deploy выполняется только на self-hosted runner с нужным набором label;
- workflow использует `concurrency`, чтобы не запускать две выкладки в production
  одновременно;
- каждая область после применения проходит свой smoke-путь.

Это не делает систему «неубиваемой», но хорошо снижает шанс случайной
выкладки и делает путь выпуска достаточно предсказуемым для single-node `k3s`
контура.

## Последовательность и безопасность production-деплоя

Оба CD workflow используют общий `concurrency group`:

- `k3s-prod-deploy`

`cancel-in-progress: false` выбран специально. Если один production deploy уже
идет, следующий не должен его обрывать посередине. Он должен дождаться своей
очереди.

Дополнительные защитные рамки:

- у workflow есть `environment: production`;
- manual deploy требует `confirm_prod=DEPLOY`;
- runner labels ограничивают место выполнения;
- deploy идет только через runner с private доступом к кластеру.

## Что считается успешным деплоем

Для этого контура успешный деплой означает не просто зеленый GitHub job.

Успехом считаются одновременно три условия:

- `helmfile sync` для нужной области завершился без ошибок;
- проверки для конкретной области завершились без ошибок;
- workflow записал осмысленный summary с примененной областью и `ref`.

Если job деплоя зеленый, но проверки после выкладки упали, релиз считается
неуспешным.

## Модель отказа

Сейчас контур рассчитан на простую и понятную эксплуатационную модель.

Если деплой падает:

- GitHub Actions сохраняет лог шага выкладки;
- затронутая область известна явно;
- команда может перезапустить либо ту же область, либо полный деплой из manual
  workflow;
- разбор проблемы делается на runner и в кластере стандартными `kubectl`,
  `helmfile` и observability-инструментами.

Rollback как отдельная автоматика в этот документ не входит. Текущая модель
делает ставку на предсказуемое повторное применение, изоляцию областей и
smoke-проверки после каждого применения.
